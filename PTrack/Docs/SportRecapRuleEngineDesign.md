# Sport Recap Rule Engine Design(运动回顾 · 千人千面规则引擎)

## 背景

Movinn 目前的轨迹热图偏"数据统计",用户看到的是数字本身。运动回顾的目标是回答"所以我该怎么办":

- 综合过去一周的睡眠,告诉用户接下来怎么睡。
- 综合过去一周/几天的步数、运动负荷,判断状态与风险,给出行动建议。
- 单次运动结束后(或当天累计),结合睡眠与身体指标,动态给出今晚几点上床、今天怎么吃。

约束与定位:

- **不接入任何大模型**(云端或本地都不依赖)。个性化来自"用户自身滚动基线 + 确定性规则 + 模板文案",天然千人千面、可离线、可单测、零 API 成本,符合 Movinn "仅在本地处理"的隐私定位。
- 参考了 Momentum Apple Health MCP 与 ChatExcel 健康报告的**报告结构**(指标卡 / 趋势 / 覆盖率 / 行动建议),但不采用其"数据喂给 AI"的技术路线;分析分工借鉴 guizang-sports-skill 的"先用确定性分析器算清楚"原则,把"AI 解释"环节替换为规则打分 + 模板渲染。
- 所有输出是**生活方式建议,不是医疗结论**,详见「安全红线」。

## 数据源

### HealthKit 读取项(按天聚合)

| 数据 | HK 类型 | 聚合方式 | 用途 |
| --- | --- | --- | --- |
| 睡眠 | `sleepAnalysis`(category,iOS16+ 含 core/deep/REM/awake 分期) | 按"睡眠日"合并区间,取总时长、入睡/醒来时刻、睡眠中点 | 场景 A / C |
| 步数 | `stepCount` | `cumulativeSum` | 场景 B |
| 静息心率 | `restingHeartRate` | `discreteAverage` | 恢复信号 |
| HRV | `heartRateVariabilitySDNN` | `discreteAverage` | 恢复信号 |
| 活动能量 | `activeEnergyBurned` | `cumulativeSum` | 负荷估算兜底 |
| 锻炼时长 | `appleExerciseTime` | `cumulativeSum` | 活动量达标 |
| 体重 | `bodyMass` | 最近一次 | 营养建议按 g/kg 换算(缺失则退化为固定范围) |
| 锻炼记录 | `HKWorkout` | 逐条 | 场景 B / C 的运动事实 |

- 统一用 `HKStatisticsCollectionQuery` 按自然日聚合,交给系统处理多来源去重。
- Strava 同步的 `TrackedWorkout` 与 HKWorkout 的去重复用现有 `WorkoutSyncCoordinator` 逻辑;Strava 侧保持现有字段,不扩展。

### 扩展字段(尽可能多读,按建议价值分档)

**第一档:直接增强三大场景,P2 就读**

| 数据 | HK 类型 | 能给出的建议 |
| --- | --- | --- |
| 运动后 1 分钟心率恢复 | `heartRateRecoveryOneMinute`(iOS 16+) | 恢复力趋势:环比自身基线上升 → 体能进步肯定;单次明显低于基线 → 与恢复信号规则联动,建议低强度日 |
| 最大摄氧量 | `vo2Max` | 苹果自算的体能长期指标,直接引用不自造:8 周下降 >5% → 建议增加有氧基础量;创个人新高 → 正向反馈 |
| 日照时长 | `timeInDaylight`(iOS 17+) | 昼夜节律联动:日照 < 30min 且睡眠中点持续后移 → "白天出门 15 分钟"比"早点睡"更有效的干预点 |
| 站立小时 / 站立时间 | `appleStandHour` / `appleStandTime` | 久坐检测从"日步数"细化到"小时级":连续多日站立 < 8 小时 → 每小时起身提醒建议;区分"运动了但全天久坐"的隐性风险 |
| 爬楼层数 | `flightsClimbed` | 零成本爬升习惯信号,与骑行/徒步爬升数据互补,用于正向肯定类规则 |
| 睡眠呼吸频率 | `respiratoryRate`(睡眠期) | 基线偏移是身体异常最早的信号之一:z > 2 连续 2 晚 → 保守文案"身体可能正在对抗什么,建议今明两天降低强度"(不下诊断) |
| 基础能量 | `basalEnergyBurned` | 与活动能量合成全天消耗背景,让场景 C 的营养区间更贴合当日实际 |
| 体力投入 / 主观强度 | `physicalEffort`(iOS 17+)/ `workoutEffortScore`(iOS 18+,用户打分) | **负荷计算升级为 sRPE(时长 × 主观强度)**,ACWR 更准;用户打过分的运动优先采用 |

**第二档:跑者/骑行者专项,P3 接入**

| 数据 | HK 类型 | 能给出的建议 |
| --- | --- | --- |
| 跑步动态 | `runningStrideLength` / `runningVerticalOscillation` / `runningGroundContactTime` / `runningPower`(iOS 16+) | 对比自身基线的跑姿效率:长距离后半程垂直振幅显著升高 → 疲劳时跑姿劣化提示;触地时间趋势改善 → 正向反馈 |
| 骑行功率/踏频 | `cyclingPower` / `cyclingCadence`(iOS 17+) | 强度分布陈述(类似热图页风格);**不推算 FTP、不做训练区间处方** |
| 步行速度/步态 | `walkingSpeed` / `walkingStepLength` | 连续多日低于基线 → 疲劳佐证信号(只作为组合证据,不单独触发) |
| 腕温 | `appleSleepingWristTemperature`(iOS 17+) | 偏离基线 +0.5°C 连续 2 晚 → 与呼吸频率规则组成组合证据,同样只建议减量不下结论 |

**第三档:机会型,用户有记录才启用**

| 数据 | HK 类型 | 能给出的建议 |
| --- | --- | --- |
| 饮水 | `dietaryWater` | 有记录时把场景 C 的补水提示变成缺口量;无记录不提 |
| 饮食记录 | `dietaryEnergyConsumed` 等 | 仅当用户本来就在记录时,把营养建议从"范围"细化为"今天还差约 xx";绝不主动引导记录热量 |
| 正念记录 | `mindfulSession` | 恢复信号触发时,若用户有正念习惯则在建议里引用它 |
| 心情记录 | `stateOfMind`(iOS 17+) | 关联洞察:"有运动的日子,你记录的心情更积极"(需双侧样本 ≥ 8) |
| 经期周期 | `menstrualFlow` 等 | **可选且默认关闭**,用户显式开启后才读:周期阶段与负荷安排的通识建议;文案极保守 |

**明确不读的字段(医疗红线)**:心电图、房颤/不规则心律通知、血压、血糖、血氧异常事件、睡眠呼吸暂停通知、步行稳定性(跌倒风险)。这些属于医疗范畴,任何"建议"都可能构成误导。

**授权策略**:按档分批请求授权(P2 只请求第一档 + 基础项),每个字段独立可拒;被拒字段对应规则静默关闭,不降级其他功能、不反复索权。

### 本地日聚合缓存

新增 `DailyWellnessSample`(SQLite/文件缓存,与现有 store 风格一致):

```swift
struct DailyWellnessSample: Codable {
    let day: Date                      // 自然日(用户时区)
    var sleepDurationMinutes: Double?  // nil = 未记录,严禁当 0
    var sleepMidpointMinutes: Double?  // 距 0 点的分钟数,可为负(前一晚)
    var deepSleepMinutes: Double?
    var stepCount: Double?
    var restingHeartRate: Double?
    var hrvSDNN: Double?
    var activeEnergyKilocalories: Double?
    var exerciseMinutes: Double?
    var workoutLoad: Double?           // Σ(时长 × 强度系数),见下文
    var coverage: DataCoverage         // 每字段有/无记录的位图
}
```

**覆盖率是一等公民**:每条建议的触发都有最低覆盖率门槛;没戴设备的日子在 UI 中显示"未记录",不参与均值。

## 个人基线(千人千面的来源)

对每个指标维护滚动基线,判断永远相对于用户自己:

- `baseline28`:近 28 天中位数(抗异常值)。
- `ewma7`:7 天指数加权均值(近期状态)。
- `sigma28`:近 28 天绝对中位差(MAD)换算的稳健标准差,用于 z-score。
- 基线生效门槛:该指标近 28 天覆盖 ≥ 14 天,否则相关规则整体不触发(冷启动期只展示事实统计)。

**运动负荷**:`load = Σ 每次运动(分钟 × 强度系数)`,强度系数按运动类型 + 相对配速/心率分 3 档(0.75 / 1.0 / 1.3);无心率无配速时按类型默认档。在此之上计算 **ACWR(急慢性负荷比)= 7 天负荷均值 ÷ 28 天负荷均值**,运动科学通用的加量风险指标。

## 时间范围与规则分区(v1.0.8 实现)

指导页提供五个时间范围,**每个范围有专属规则集,互不重叠** —— 这是避免"切换 tab 看到同样文案"的关键。

| 范围 | 评估窗 | 判断基准 | 图表粒度 | 视角 |
| --- | --- | --- | --- | --- |
| 三天 | 3 天 | 前 28 天个人基线 | 日 | 接下来 24–48 小时怎么办 |
| 一周 | 7 天 | 前 28 天个人基线 | 日 | 本周的结构与节奏 |
| 一月 | 30 天 | 上一个 30 天 | 日 | 月度位移对比 |
| 半年 | 182 天 | 上一个 182 天 | 周 | 中期规律性与里程碑 |
| 一年 | 365 天 | 上一个 365 天 | 月 | 长期趋势、习惯与季节性 |

规则归属:

- **三天**:今晚上床时刻、入睡后移、恢复信号、HRV 良好、间隔过长、连续运动 + 即时补给类营养
- **一周**:睡眠债、作息波动、持续偏短、周末时差、睡眠稳定、深睡占比、日照不足、ACWR 加量/回落、久坐、周达标、静息心率改善、步数稳定 + 结构性营养
- **一月**:睡眠均值位移、运动总量位移、距离 PB、训练量上升期营养
- **半年**:周规律性、步数位移、里程碑(半年文案)、长期营养基础
- **一年**:静息心率长期趋势、运动日习惯识别、季节性分析、里程碑(年度文案)、长期营养基础(年度文案)

## 三大场景规则设计

每条规则输出统一结构:

```swift
struct RecapAdvice {
    let category: RecapAdviceCategory  // sleep / activity / nutrition / recovery / risk / positive
    let priority: Int                  // 展示排序,风险类恒为 0
    let evidence: String               // 依据,如"近 7 天平均睡眠 6.2h,低于你的基线 7.1h"
    let title: String
    let body: String
    var tip: String?                   // 同类别知识点,渲染为品牌绿圆点独立一行
    let score: Double                  // 幅度 × 置信度
}
```

### 场景 A:睡眠 → 怎么睡

门槛:评估窗内睡眠覆盖 ≥ 70% 天数(至少 2 天);基线需近 28 天覆盖 ≥ 14 天。

| 规则 | 归属范围 | 触发条件 | 建议输出 |
| --- | --- | --- | --- |
| 今晚上床时刻 | 三天 | 昨晚时长低于基线,`advance = min(缺口×0.5 + 负荷加成, 60min) ≥ 10min` | 给出今晚具体上床时刻与提前分钟数,强调当天补比周末补有效 |
| 睡眠债 | 一周 | `debt = Σ max(0, baseline28 − 当日时长)` > 天数×26min | 未来 3 晚提前上床,提前量 = `min(debt/3, 60min)`,给出具体时刻 |
| 作息波动 | 一周 | 睡眠中点标准差 > 90min | 固定上床窗口(用户自己中点 ±30min),说明规律比补时长更有效 |
| 持续偏短 | 一周 | ewma < 6h 且 baseline28 ≥ 6.5h | 指出连续偏短趋势 |
| 周末补偿 | 一周 | 周末均值 − 工作日均值 > 90min | 提示社交时差,工作日窗口小步前移 |
| 睡眠稳定 | 一周 | 覆盖足够且均值贴近基线、中点 σ ≤ 45min | 正向反馈(不能只有问题,需肯定型规则托底) |
| 入睡后移 | 三天 | 睡眠中点较基线晚 > 45min | 提示无感漂移,今晚回拨 20 分钟 |
| 深睡偏低 | 一周 | 深睡占比 < 11% | 睡前咖啡因/强光提示,注明设备深睡为估算值 |
| 日照不足 | 一周 | 日均 `timeInDaylight` < 30min | 上午出门 15 分钟,比强迫早睡更有效的节律干预 |
| 睡眠均值位移 | 一月 | 本期 vs 上期相差 ≥ 20min | 双向(改善/下滑)文案 |

### 场景 B:活动量与风险 → 怎么动

门槛:步数/负荷规则各需 28 天基线生效(负荷另需 ≥ 8 个活动日)。

| 规则 | 归属范围 | 触发条件 | 建议输出 |
| --- | --- | --- | --- |
| 加量过快 | 一周 | ACWR > 1.5 | **风险类**:本周负荷是近月 x.x 倍,下周回落,优先低强度 |
| 明显回落 | 一周 | ACWR < 0.6 | "恢复到基线"的最小行动(2 次 × 基线单次时长) |
| 久坐趋势 | 一周 | 连续 ≥ 5 天步数 < max(5000, 0.6 × baseline28) | 按用户基线定制的日步数目标(不是统一 1 万步) |
| 恢复信号 | 三天 / 一周 | RHR 连续 3 天 ≥ 基线 +5bpm(HRV ≤ 基线 ×0.8 时追加佐证) | **风险类**:建议 1–2 天低强度,含"如伴随不适请咨询专业人员" |
| 恢复良好 | 三天 | HRV ewma ≥ 基线 × 1.15 | 提示近期适合安排强度课 |
| 间隔过长 | 三天 | 有训练习惯但连续 ≥ 4 天无运动 | 轻推:今天一次轻松的就够 |
| 连续运动 | 三天 | 连续 ≥ 3 天有运动 | 肯定势头 + 提醒留恢复日 |
| 周达标 | 一周 | 周锻炼 ≥ 150min(WHO) | 正向反馈 |
| 静息心率改善 | 一周 | RHR ewma 低于基线 ≥ 3bpm | 正向:有氧能力提升的可靠信号 |
| 步数稳定 | 一周 | ≥ 70% 天数达到基线以上 | 正向:日常活动底盘扎实 |
| 运动总量位移 | 一月 | 本期 vs 上期 ±25% | 双向文案(上升提醒循序渐进,下降给最小行动) |
| 距离 PB | 一月 | 单次最长距离超过上期 | 正向 |
| 周规律性 | 半年 | 有运动的周占比 ≥ 80% / < 50% | 双向文案 |
| 步数位移 | 半年 | 本期 vs 上期 ±15% | 双向文案 |
| 里程碑 | 半年 / 一年 | 累计距离 ≥ 100km | 半年与年度各一套文案 |
| 静息心率长期趋势 | 一年 | 本期 vs 上期 ±3bpm | 双向,上升侧含就医提示 |
| 运动日习惯 | 一年 | 某星期几占运动日 ≥ 40% | 点出"你的运动日是周 X",星期名按语言本地化 |
| 季节性 | 一年 | 最活跃月 / 最少月 ≥ 2 倍(仅统计记录 ≥ 20 天的月) | 建议给淡季准备替代方案 |

### 场景 C:营养 → 怎么吃

营养规则**按范围分流**,只依赖客观事实,给范围不给处方,不做减重/疾病饮食/补剂建议。

| 规则 | 归属范围 | 触发条件 | 建议输出 |
| --- | --- | --- | --- |
| 糖原补充(即时) | 三天 | 存在 ≥ 60min 的运动 | 聚焦最近一次:24 小时内碳水优先于蛋白质 |
| 蛋白质(即时) | 三天 | 运动合计 ≥ 天数×13min | 接下来两餐各加一份,给出常见食物等价物 |
| 碳水补充(结构) | 一周 | 存在 ≥ 60min 的运动 | 运动后 1–2h 内补主食类碳水 |
| 蛋白质(结构) | 一周 | 同上门槛 | 20–30g 分散到三餐,给等价食物 |
| 补水与电解质 | 三天 / 一周 | 单日消耗 ≥ 500kcal 或存在 ≥ 90min 运动 | 少量多次;超 1 小时补钠 |
| 进食节律 | 三天 / 一周 | 平均睡眠 < 6.5h | 睡眠不足推高食欲,正餐安排在睡前 2h 以上 |
| 低活动期 | 一周 | 运动量低于门槛 40% | 不必额外加餐,保持蛋白质与蔬菜基本量 |
| 训练量上升期营养 | 一月 | 本期运动量 ≥ 上期 ×1.25 | 提醒"吃太少"比"吃太多"更常见 |
| 长期营养基础 | 半年 / 一年 | 折合周均 ≥ 150min | 强调日常三餐稳定性;年度另有专属文案 |

> 说明:体重字段已申请授权,但当前版本的营养建议统一给通用区间与食物等价物,未按 g/kg 换算,避免体重缺失时的降级分支。

## 文案丰富度机制

- **补充提示池**:每条建议末尾追加一句同类别知识点(睡眠 5 / 运动 5 / 饮食 5 / 恢复 4 / 正向 4,共 23 句),UI 上渲染为**品牌绿小圆点**开头的独立一行,不使用"顺带一提"这类模板前缀。
- **确定性轮换**:`index = (stableHash(周期ID) + stableHash(建议标题)) % 池长度`。同一份报告内容稳定、不同建议拿到不同提示、随周期推进自动换新。
- `stableHash` 为自实现的 DJB2(UInt64 域内运算),不能用 `String.hashValue`——后者每次启动的种子不同,会导致同一份缓存重新生成后提示句乱跳。

## 引擎架构(实际文件)

```
WellnessHealthKitReader   HealthKit → 日聚合(nonisolated,串行 assemblyQueue 组装)
        ↓
DailyWellnessSample       日聚合样本(nil = 未记录,严禁当 0;workoutLoad 无运动才为 0)
        ↓
WellnessBaseline          中位数 / MAD 稳健标准差 / EWMA / 跨零点时刻归一化
        ↓
WellnessRuleEngine        按 range 分区跑规则 → 打分 → 选取 → 追加提示 → 组装内容块
        ↓
WellnessRecapStore        按"范围 × 周期 × 语言 × schema"缓存,主线程编排(MainActor)
        ↓
WellnessRecapViewController + RecapContentViews   半屏 sheet、打字机、柱状图、指标表
```

**选取策略**(`select`):风险类全部保留置顶;其余按维度轮转 —— 先每个维度(睡眠→运动→饮食→恢复→正向)各取分数最高的一条,再第二轮、第三轮,直到每类 3 条或总数 10 条。轮转是为了保证多维度覆盖,纯按分数排序会让睡眠类占满名额。

**没有兜底规则**:某维度没有可靠信号时该建议就不出现,不用通用文案凑数。

**内容块**:`RecapBlock` = heading / paragraph / metricTable / chart / advice / footnote,顺序为 总结 → 数据概览表 → 趋势图 → 建议。

**并发与健壮性**:

- 同范围重复请求的回调**排队**,生成完统一 fan-out,避免并发请求拿到 nil 被误判为"无数据"。
- 25 秒兜底超时释放生成占位,防止 HealthKit 回调不返回导致该范围永久卡死。
- 缓存是 stale-while-revalidate:先显示缓存秒开,同时用最新数据重算,内容变化(比较编码后的块数据)才替换。
- 新运动入库(`appendWorkoutsToList`)时作废全部缓存并重算。

## 安全红线

1. 不输出诊断、疾病、用药、补剂结论;恢复信号类文案必须含"仅供参考,如伴随不适请咨询专业人员"。
2. 缺失 ≠ 零:覆盖率不达门槛的规则不触发;UI 呈现覆盖率。
3. 不做统一人群标准的机械对比(如"你不如平均人"),人群阈值(WHO 150min、睡眠 7-9h)只作为双轨参考出现在文案中,判断主体永远是个人基线。
4. 睡眠/营养建议幅度设上限(提前上床 ≤ 60min,不建议节食),避免极端输出。
5. 回顾页底部固定免责声明(复用现有 `recommendation-disclaimer` 风格文案)。

## 触发与展示时机

**入口与付费墙**:首页 header 的 "Movinn" title 可点击。点击后先 `ensureAccessResolved()`,**非 Pro 用户弹付费墙**,购买成功后自动继续打开指导页。付费墙权益列表首条为「根据你的运动数据提供指导建议」。

**扫光提示**:标题上做一次从左到右的高光扫过(`HeaderTitleShimmer`),整体一道光扫过 "Movin"+"n",循环 10 次。

- 触发条件:有未查看的新分析 **或** 用户尚未解锁 Pro(后者用于持续引导点击)。
- 新分析的判定:新运动入库、重算后内容与缓存不同、新版本首次启动(按 `CFBundleShortVersionString` 记录)。
- 实现:标签自身渲染为蒙版、动 gradient 的 `locations` 而非图层位置,高光只出现在字形上且不错位;用 `animationDidStop(finished:)` 判断移除,避免重入时新旧扫光互相取消。

**首次引导气泡**(`HeaderTitleTipView`):标题下方的箭头气泡「👆 点这里,看看基于你运动数据的指导建议」。仅点击气泡或点击标题才消失(不自动消失),只展示一次,标记键含版本号(`wellnessRecap.headerTipShown.v2`),递增即可让它重新出现。

**弹窗形态**:

- `UISheetPresentationController`,detents = `[.medium(), .large()]`,默认 `.medium`,带 grabber。
- 顶部固定:标题「指导建议」+ 五个时间范围分段控件(默认**三天**);底部固定:居中免责声明(不跟随安全区)。
- 视觉层级:页面底色为淡灰(`groupedCardBackground`),内容模块为白/黑承载卡(`solidBackground`)。建议合并进同一张卡、内部细线分隔;概览表与每张趋势图各自成卡;小标题与总结留在灰底上。
- 中日韩文本使用两端对齐并清空 `lineBreakStrategy`,否则 "15 分钟" 这类数字+量词组合会被整体推到下一行,右边缘参差。

**打字机动画**:

- 块级顺序播放:文本块逐字揭示,表格/图表淡入,自动跟随滚动。
- 实现为整篇先以透明色完整排版,再按**合成字符边界**逐段恢复真实颜色,布局稳定、不切开 emoji;`CADisplayLink` 驱动约 45 字/秒(通过弱引用 proxy 持有,避免标签无法释放)。
- 点击任意处跳过;同一「范围 × 周期」只播一次;`UIAccessibility.isReduceMotionEnabled` 时直接全量显示。

**生成与缓存**:

- App 启动/进前台后台预生成默认范围(仅在已请求过授权时,绝不触发系统授权弹窗)。
- 缓存键 = `schema版本 × 范围 × 周期ID × 语言`。周期 ID:短周期按天滚动,月/半年/年按自然周期。
- **改动块顺序或规则集时必须递增 `schemaVersion`**,否则会命中旧缓存(当前为 8)。
- 冷启动/无授权时降级为授权引导,保证入口点开永远有内容。

### 已知取舍

- 营养建议未按体重 g/kg 换算,统一给通用区间(体重字段已授权,后续可升级)。
- 拼图背景下的多 Live Photo 与 3D 动画导出已支持;但拼图内的 Live 图块在 3D 模式下不参与二次合成的边界情况未覆盖。
- 规则命中依赖数据密度:近 28 天覆盖不足 14 天时,大部分规则静默,页面只显示概览与趋势。

## 测试策略

- 规则层:构造固定的 `DailyWellnessSample` 序列做快照测试(睡眠债、ACWR 边界、覆盖率门槛、冷启动、各范围规则不重叠)。
- 模板层:遍历全部规则 × 全部语言 × 全部提示池渲染一遍,断言无缺槽位、无 `String(format:)` 参数错配。
- 边界:全空数据、单日数据、跨时区、夜班作息(睡眠中点在白天)、白天小睡、多来源睡眠重叠不崩溃且不出错误建议。
